# Dokument-Assistent: план разработки

Технический план для пошаговой разработки. Этот документ — контекст проекта: при работе над задачами следовать описанным здесь решениям, конвенциям и порядку фаз. Не перепрыгивать фазы и не расширять scope без явного запроса.

---

## 1. Что строим (кратко)

Личный секретарь по немецкой бюрократии. Пользователь загружает фото/PDF письма → система анализирует его через LLM → создаёт структурированную карточку документа → сохраняет оригинал в Google Drive, карточку в Notion, дедлайн в Google Calendar. Сначала single-user инструмент для себя (Этап 0 бизнес-плана), потом ближний круг, потом публичный продукт.

## 2. Стек и архитектурные решения

**Backend:** Java 21, Spring Boot 3.x, Maven. Модульный монолит — никаких микросервисов: один деплоймент, разделение на пакеты по доменам (`ingestion`, `analysis`, `storage`, `integrations`, `cards`). Микросервисы — осознанно нет: solo-проект, преждевременная сложность.

**Frontend:** React 18 + TypeScript + Vite, Tailwind CSS, TanStack Query для серверного состояния. Без Redux — состояния мало.

**БД:** PostgreSQL 16. Flyway для миграций. JSONB для сырого результата анализа, нормализованные колонки для полей, по которым ищем/фильтруем.

**LLM:** Anthropic API (Claude) с vision — фото/PDF-страницы отправляются как изображения напрямую в модель, **отдельный OCR-движок (Tesseract и т.п.) не используем**: vision-модели справляются с немецкими письмами лучше и это минус целая подсистема. PDF с текстовым слоем — извлекаем текст (Apache PDFBox) и шлём текстом, это дешевле; сканы/фото — как изображения. Провайдер за интерфейсом `DocumentAnalyzer`, чтобы можно было сменить/добавить модель.

**Интеграции:** Google Drive API, Notion API, Google Calendar API. На Этапе 0 — авторизация через мои собственные credentials (OAuth для Google с refresh token, internal integration token для Notion), конфигурируется через env. Мульти-юзерный OAuth — только в фазе 6.

**Инфраструктура Этапа 0:** docker-compose (postgres + app), запуск локально на моей машине. Никакого облака, CI/CD-минимум (GitHub Actions: build + tests).

**Секреты:** только через переменные окружения / `.env` (в `.gitignore`). Никаких ключей в коде и коммитах.

## 3. Доменная модель

Центральная сущность — `DocumentCard`:

```
document_card
  id                UUID PK
  created_at        timestamptz
  original_filename text
  source_type       enum: PDF_TEXT | PDF_SCAN | IMAGE
  language          text            -- язык оригинала (de, en, ...)
  doc_type          enum: INVOICE | REMINDER_MAHNUNG | INSURANCE | TAX | 
                          BANK | RENTAL | EMPLOYMENT | MEDICAL | SCHOOL_KITA |
                          GOVERNMENT | CONTRACT | INFO_ONLY | OTHER
  sender_name       text
  sender_category   text            -- Finanzamt, AOK, Vermieter...
  document_date     date
  deadline          date            -- nullable
  amount_value      numeric         -- nullable
  amount_currency   text
  reference_numbers jsonb           -- {kundennummer, aktenzeichen, iban, ...}
  summary           text            -- "что это" одним абзацем, на языке пользователя
  required_action   enum: PAY | RESPOND | SEND_DOCUMENTS | ATTEND | NONE_ARCHIVE
  action_steps      jsonb           -- список конкретных шагов
  urgency           enum: HIGH | MEDIUM | LOW | NONE
  confidence        enum: HIGH | MEDIUM | LOW
  evidence_quotes   jsonb           -- цитаты из оригинала, на которых основаны выводы
  raw_analysis      jsonb           -- полный ответ LLM как есть
  status            enum: NEW | IN_PROGRESS | DONE | ARCHIVED
  drive_file_id     text            -- nullable до выгрузки
  drive_link        text
  notion_page_id    text
  calendar_event_id text
```

`evidence_quotes` обязательны: каждый вывод (дедлайн, сумма, требуемое действие) должен сопровождаться цитатой из оригинала — это основа доверия и проверки ошибок модели.

## 4. Контракт анализа (LLM)

`DocumentAnalyzer.analyze(document) -> AnalysisResult` — модель обязана вернуть строгий JSON по схеме, повторяющей поля карточки + поле `confidence_reasoning`. Правила промпта:

- отвечать только JSON, без markdown-обёрток;
- язык `summary` и `action_steps` — русский (конфигурируемо);
- если поле не найдено — `null`, не выдумывать;
- для каждого из полей deadline / amount / required_action — цитата-обоснование в `evidence_quotes`;
- `confidence: LOW`, если скан плохого качества, документ многозначен или тип не определён; в этом случае `summary` должен явно содержать рекомендацию показать документ человеку.

Парсинг ответа — с валидацией (jackson + bean validation), при невалидном JSON — один retry с указанием на ошибку, потом fail с сохранением сырого ответа для разбора.

## 5. Фазы разработки

Каждая фаза заканчивается работающим инкрементом. Definition of Done фазы: код собирается, тесты зелёные, фича проверена руками на реальном письме, README обновлён.

### Фаза 0 — скелет (1–2 вечера)
Монорепо: `/backend`, `/frontend`, `docker-compose.yml`. Spring Boot app с health-эндпоинтом, Postgres в compose, Flyway с первой миграцией, React-заготовка с Vite, прокси на backend. GitHub Actions: build + test. **DoD:** `docker compose up` + `npm run dev` поднимают рабочую пустую систему.

### Фаза 1 — пайплайн анализа (ядро)
Эндпоинт `POST /api/documents` (multipart: PDF/JPG/PNG). Определение типа источника (текстовый PDF / скан / фото), извлечение текста через PDFBox или подготовка изображений. `DocumentAnalyzer` на Anthropic API. Сохранение `DocumentCard` в Postgres. `GET /api/documents/{id}`, `GET /api/documents` (пагинация). Учёт стоимости: логировать токены и расчётную цену каждого анализа в отдельную таблицу `analysis_cost` — пригодится для экономики продукта.
**DoD:** загружаю реальное письмо curl-ом → в БД корректная карточка с цитатами.

### Фаза 2 — минимальный UI
Страница загрузки (drag-n-drop + камера на мобильном через `<input capture>`), экран карточки (summary, действия, дедлайн, сумма, цитаты, индикатор уверенности — визуально заметный при LOW), список документов с фильтрами по типу/статусу/дедлайну, смена статуса. PWA-манифест, чтобы добавить на домашний экран телефона.
**DoD:** фоткаю письмо телефоном → через минуту вижу понятную карточку.

### Фаза 3 — интеграции хранения
Google Drive: выгрузка оригинала в структуру `/Dokumente/{год}/{категория}/{дата}_{отправитель}.pdf`, сохранение ссылки в карточке. Notion: создание страницы в базе с полями карточки + ссылкой на Drive (схему Notion-базы зафиксировать в README). Идемпотентность: повторная выгрузка не плодит дубликаты. Выгрузка асинхронная (Spring events / @Async), статус выгрузки виден в UI.
**DoD:** новое письмо автоматически появляется и в Drive, и в Notion.

### Фаза 4 — дедлайны и напоминания
Google Calendar: при наличии дедлайна — событие с напоминаниями (за 7 и за 2 дня, конфигурируемо), название вида «Ответить AOK: подтверждение адреса». Дашборд «ближайшие дедлайны» на главной. Подтверждение пользователем перед созданием события (дедлайн мог быть распознан неверно).
**DoD:** письмо с дедлайном → подтверждённое событие в календаре.

### Фаза 5 — качество и батч-прогон
Команда/эндпоинт для пакетной обработки папки с накопившимися письмами. Прогон всего личного архива за последние месяцы. По результатам: фиксация ошибок анализа в `analysis_feedback` (поле «что модель поняла неверно»), итерация промпта, при необходимости — few-shot примеры проблемных типов писем. Вопросы по документу: `POST /api/documents/{id}/questions` — чат с контекстом конкретного документа.
**DoD:** ≥90% писем из личного корпуса разобраны без существенных ошибок; ошибки задокументированы.

*— здесь заканчивается Этап 0 бизнес-плана. Месяц ежедневного использования. Дальше — только если пройден критерий «пользуюсь сам каждый день». —*

### Фаза 6 — ближний круг (Этап 1)
Аутентификация (Spring Security, для начала magic link или Google OAuth login). Мульти-юзерность: `user_id` во всех таблицах, изоляция данных. OAuth-подключение собственных Google Drive / Notion / Calendar каждым пользователем; упрощённый режим без интеграций (карточки только в приложении). Опционально: Telegram-бот как альтернативная точка загрузки. Rate limiting и лимит документов на пользователя.

### Фаза 7+ — публичный продукт (Этап 2, отдельное планирование)
Биллинг (подписки), лендинг, GDPR-обвязка (Datenschutzerklärung, AVV, удаление данных по запросу), деплой в EU-облако (Hetzner), мониторинг. Планируется отдельно после валидации Этапа 1.

## 6. Конвенции разработки

- **Тесты:** unit на парсинг/маппинг ответа LLM (с замоканными ответами), integration на REST-слой (Testcontainers + Postgres). LLM-вызовы в тестах всегда мокаются; реальные вызовы — только в ручных smoke-сценариях.
- **Ошибки внешних API:** retry с backoff (resilience4j), любые сбои интеграций не теряют документ — карточка сохраняется, выгрузка повторяется позже.
- **Логирование:** structured logging (JSON), без содержимого документов в логах — там персональные данные.
- **Git:** trunk-based, маленькие коммиты по фазам, Conventional Commits.
- **Язык кода:** английский (код, коммиты, README); язык продукта (UI, summary) — русский.

## 7. Как работаем по этому плану (инструкция для сессий)

1. В начале сессии: назвать текущую фазу и конкретный шаг внутри неё.
2. Двигаться маленькими инкрементами: один шаг — один работающий результат с тестами.
3. Не добавлять фичи из будущих фаз «раз уж мы здесь». Любое отклонение от плана — сначала обсудить и зафиксировать правкой этого документа.
4. После завершения фазы — обновить статус ниже.
